# 10 — API & Integration Contracts (v1 — additive only)

## 10.1 Conventions
Base `/api/v1` (alias `/api` → v1). Auth: `Authorization: Bearer <jwt>`; mutating calls accept `Idempotency-Key`. Errors: `{code, message, trace_id, retryable}`. Codes: 400 VALIDATION, 401/403 AUTH, 404 NOT_FOUND, 409 CONFLICT/DEDUPE, 410 APPROVAL_EXPIRED, 422 RISK_REJECT (with `risk_code`), 429 RATE, 501 NOT_IMPLEMENTED, 503 DEGRADED.

## 10.2 Endpoints
- `POST /api/watches {symbol, direction, trigger, invalidation, expires_at?, regime_filter?}` → 201 `{id, version, status}`. `regime_filter` is an optional boolean (default `false`, null treated as absent) persisted on the watch row: when `true` the Worker evaluates the ETHBTC / USDT.D / BTC.D / TOTAL3 regime **at analysis time** (docs/08 §8.2a). The row is inserted `DRAFT` v1 and **published to `ACTIVE` v2 in the same batch** (docs/05 §5.3 edge `DRAFT→ACTIVE`, reason `publish (stalk)`), writing `watch_transitions` + `watch.created_v1` + `watch.activated_v1` + an outbox row. The Stalk click IS the human publish: only `ACTIVE` watches are evaluated (Go cold start `GET /api/watches/active-snapshot`, the ADR-004 poller set), so a draft left unpublished would never arm. Arming is advisory — a trigger still leads to analysis, and every order needs its own single-use human approval (SAFE-002). 409 on duplicate open watch (same symbol+trigger hash).
- `GET /api/watches?status=ACTIVE` · `GET /api/watches/active-snapshot` (Go boot; full ACTIVE set + versions).
- `POST /api/signals:ingest {watch_id?, kind, payload, source}` → 201 `{id}`. Kinds: DIVERGENCE_TRIPLE|ORDER_BLOCK|OB_OS|MTF|REGIME.
- `POST /api/analysis:runs {watch_id}` → 201 `{id, bias, confidence, model, input_hash, strategy_version, regime, engine{analyze_id, strategies, data_sources, verdicts, suggest_zones}}` (advisory). The run is computed by the LIVE Go engine (`GET {GO_WATCHER_URL}/strategies/registry` for the pinned strategy set, then `POST /analyze` with the watch's symbol+direction) and the row stores the engine's own aggregate plus per-timeframe provider provenance — there is no local fallback, so an unreachable engine is `503 DEGRADED` and **no row is written**; an unknown `watch_id` is `404 NOT_FOUND`. The one exception is a regime veto: when the watch opted in and the pre-analysis gate returns `VETO`+`BLOCK`, the run is stored as `{bias:"FLAT", confidence:0, model:"regime-filter", engine:null, regime:{verdict:"VETO", regime, reason, confidence_penalty, force_flat, detail{index_trend,vetoed_by,action_on_veto}}}` **without calling the engine**; on `WARN`/`PASS` the engine runs and `confidence = engine.confidence × (1 − regime.confidence_penalty)`. `regime` is `null` when the watch did not opt in (docs/08 §8.2a).
- `POST /api/approvals {watch_id, analysis_id, decision, reason}` → 201 `{id, decision, expires_at, state}` + `approval.granted_v1|rejected_v1` audit event. Consume is invoked by the submit path (E09), surfacing `410 APPROVAL_EXPIRED` / `409 CONFLICT`; the expiry sweeper runs on a 60s cadence.
- `POST /api/orders:intents {approval_id, side, qty, leverage, stop_loss?}` → 201 `{intent_id, client_order_id, order_status, exchange_order_id}` or `422 {risk_code, detail}`; a consumed approval → `409 CONFLICT`, an expired one → `410 APPROVAL_EXPIRED`, a fenced caller → `503 DEGRADED`. Identity (`client_order_id`) is derived server-side; the price comes from our own market data, never the caller. `stop_loss` is OPTIONAL and advisory (a decimal string, direction-checked by the risk gate → `R-NOT`); it is stored on the intent and passed to the venue, and it never places an exit order by itself (docs/08 §8.6).
- `GET /api/orders:intents` · `GET /api/orders` (read-only: the intent list and the exchange-side `orders` rows with `status`, `fills_json`, `last_reconciled_at`). The chat operator snapshot reads both (docs/18 §18.3a); neither route can submit or mutate anything.
- `POST /api/kill-switch {engaged, reason, confirm?}` → 201 engage (operator+), 200 release (admin + `confirm: true`, else 400/403).
- `POST /api/watches:trigger {watch_id, kind: TRIGGERED|INVALIDATED, px, prev_px, seq, watch_version?, ts?}` → 201 `{watch_id, status:"ANALYZED", analysis_id, bias, confidence, model, engine}` when the analysis ran, 200 `{... status:"INVALIDATED"}` for an invalidation, 200 `{duplicate:true}` for a replay, 200 `{ignored: "not ACTIVE (…)" | "stale evaluation (…)"}` when the loop's view was stale, and 202 `{status:"TRIGGERED", analysis_degraded}` when the engine was unreachable (the edge is recorded, the run is not). Auth: `x-agent-token` (`GO_AGENT_TOKEN` ?? `GO_HEARTBEAT_TOKEN`). The Go trigger loop is the caller; the D1 transaction (transition + `watch.triggered_v1`/`watch.invalidated_v1` event with dedupe_key `type:watch_id:seq` + outbox) lives here so the Go plane never writes D1.
- `GET /api/health` · `GET /api/recovery/log` (unchanged, E06-T01).
- AI strategy codegen (advisory, review-only — nothing builds or executes from these rows): `POST /api/strategy:generate {description, strategy_id, version}` → 201 `{id, strategy_id, version, code, model, status, attempts}` (two-shot: the fast model first, the coder model on contract failure; a rejected attempt is recorded with `status: "rejected: …"`); `POST /api/strategy:chat` / `POST /api/strategy:chat:stream` (SSE) for multi-turn advisory chat (both accept an optional client-declared `context` — the dashboard room/setup block, injected as a labelled DATA system turn, capped at 4000 bytes); `POST /api/strategy:draft {strategy_id, version, code}` → 201 `{id, status}` (save a fenced block the chat produced); `GET /api/strategy:drafts` → `{drafts:[…]}` (newest first, discarded rows excluded).
- `POST /api/strategy:draft:delete {id}` → 200 `{id, status:"deleted", kept_for_audit:true}` (200 `{already:true}` when it was already discarded), 400 without `id`, 404 unknown. **Soft delete**: `status='deleted'` — the row stays in D1 for the audit trail and leaves `GET /api/strategy:drafts`. Same rule as the watch FSM (docs/05 §5.3): a row that vanishes is unauditable. RBAC trader+; it is in the browser POST allow-list (`errors.mjs`), because a draft is review-only data and no order/approval path is reachable from it (D-08).
- Telegram alert prefs (advisory, docs/09 §9.3a): `GET /api/notify:prefs` → `{prefs:[{topic, enabled}]}` (seven topics, absent = enabled); `POST /api/notify:prefs {prefs:{TOPIC:boolean}}` → 200 `{updated:[…]}` (RBAC trader+; 400 on unknown topic). Routes enqueue `notification_outbox` rows on trigger/invalidation/analysis/approval/order/kill; the cron drains them (fail-open).
- Deep analysis timeframes: `5m|15m|1h|4h` (`POST /analyze {timeframes?}`, default `5m,15m,1h` with zones from the first = 5m scalping TF; at most 4). Klines chain per TF: Toobit → OKX → Binance (`5m` maps natively on all three venues).
- Live dashboard quotes (read-only, fail-soft): `GET /api/prices?symbols=BTCUSDT,TAGUSDT` → `{mode:"filtered", prices:{SYM:"px"}, missing:[…], at}` — ONE weight-1 venue-form request per symbol (`?symbol=BTC-SWAP-USDT`, ≤25 per call, canonical echo refused as spot, `quotes.mjs` reuses `priceUrl`/`parseQuotes`); `GET /api/prices` (no param) → `{mode:"full", prices:{…848 markets…}, stale?, cached?, at}` from ONE unfiltered weight-1 request, cached 5s in-isolate so a dashboard burst costs the venue once per TTL, stale-served on venue failure and `503 DEGRADED` with no cache. Every request spends the shared ADR-004 window with the poller, so dashboard reads can never silently walk the venue into a 429 (budget exhaustion is `429 RATE`). No symbol is ever answered with an invented price — unanswered symbols land in `missing`.

## 10.4 Exchange integration boundary (VERIFIED 2026-10-10, E02-T01)
- Public WS: `wss://stream.toobit.com/quote/ws/v1`; topics `trade` (ticks: `v`=tx id, `t`=ms, `p`=price, `q`=qty) + `markPrice` + `bookTicker`; ping/pong or disconnect ≤5min; WS symbol form `BTC-SWAP-USDT` (normalizer maps ↔ `BTCUSDT`). **REST market-data calls must send the venue form too**: `?symbol=BTCUSDT` answers Toobit's SPOT book even on `/quote/v1/contract/...`, while `BTC-SWAP-USDT` is the USDT-M perpetual (docs/ops/TOOBIT-API-FACTS.md S4). Source: official docs, full capture in `docs/ops/TOOBIT-API-FACTS.md`.
- Signed REST: base `https://api.toobit.com`; `timestamp` mandatory, `recvWindow` default 5000 max 60000; `clientOrderId` supported (confirmed on flashClose — E09 re-confirms on order endpoint); limits 3000 weight/min + 60 orders/2s; 5xx = UNKNOWN outcome (our SUBMIT_UNKNOWN).
- Fallback poll: `GET /quote/v1/contract/ticker/price` (weight 1), 5s cadence proven for ≤100 symbols (ADR-004). Token-bucket + jitter enforced.
- Deep analysis klines: `GET /quote/v1/klines` (Toobit) → `GET /api/v5/market/candles` (OKX, `CELRUSDT`→`CELR-USDT`) → `GET /api/v3/klines` (Binance), first provider that answers, 120 bars per timeframe. Every verdict carries its `data_source` and `suggest_zones` carries `source`/`bars`/`last`/`last_ts`, so a zone is never shown without the venue it was measured on — a symbol the trading venue does not list (verified: `CELRUSDT` → `-100010 Invalid Symbols`) is analyzed on a fallback venue and can never fill on Toobit.
- Trigger price feed: `GET /quote/v1/contract/ticker/price?symbol=<SYM>` — **`<SYM>` must be the venue/futures form** (`BTC-SWAP-USDT`), because the symbol form selects the book: the canonical `BTCUSDT` answers Toobit's SPOT price even on this path (docs/ops/TOOBIT-API-FACTS.md S4). The singular form answers `[{"s":"BTC-SWAP-USDT","p":"80287"}]` (weight 1 per symbol) and a canonical-form echo is refused; `?symbols=` is IGNORED and answers the whole venue in the dash form. The Go tick feed (`prices.Fetch`: Redis `px:{sym}` → Toobit → Binance) and the Worker poller both map via `normalize.ToVenue`/`venueSymbol`. Verified 2026-10-16: the Go client previously used `/api/v1/...` (a 404), so every Toobit quote silently fell through to Binance.
